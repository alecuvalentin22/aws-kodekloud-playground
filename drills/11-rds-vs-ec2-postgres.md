# Drill 11 — Managed vs self-managed PostgreSQL

**The question:** "When would you use RDS over Postgres on an instance?"

The lab runs **both**, deliberately: `postgresql` on es-01, and an RDS instance
built by Terraform. Same engine, same SQL, same Ansible modules — the difference
is entirely operational.

| | Postgres on EC2 | RDS |
|---|---|---|
| OS + engine patching | you | AWS, in a window you choose |
| backups | your `pg_dump` cron | automated snapshots + PITR |
| `postgresql.conf` | edit it | **parameter groups**; some need a reboot |
| superuser | yes | **no** — `rds_superuser` is not superuser |
| access control | `pg_hba.conf` | **security groups** |
| restore | your runbook | a **new instance** from a snapshot |
| extensions | anything | AWS's supported list only |
| failover | you build it | `multi_az = true`, DNS flips |
| cost | instance only | premium over the instance |

## The three that actually catch people

**1. No superuser.** You cannot `CREATE EXTENSION` outside AWS's list, read the
filesystem, or install untrusted procedural languages. Applications that assume
superuser fail on RDS and nowhere else.

**2. Restore creates a new endpoint.** RDS automated backups are *physical*
snapshots — restoring one produces a whole new instance with a new DNS name.
There is no "restore this one table" button. That is why the playbook also takes
a **logical** `pg_dump`: granular recovery on RDS is something you have to
arrange yourself.

**3. Security groups replaced `pg_hba.conf` as the thing that locks you out.**
Note how the lab wires it — the RDS security group's ingress rule references the
**lab security group**, not a CIDR:

```hcl
ingress {
  from_port       = 5432
  to_port         = 5432
  protocol        = "tcp"
  security_groups = [aws_security_group.lab.id]   # identity, not addresses
}
```

Instances can be replaced and IPs can change; the rule keeps working, and
nothing else in the VPC can reach the database.

## Note how Ansible reaches it

RDS has no sshd, so there is no host for Ansible to connect to, and the endpoint
is not publicly reachable so your laptop cannot see it either. `playbooks/rds.yml`
therefore targets **es-01** and points `community.postgresql` at the endpoint
with `login_host`.

That is the general pattern for managed services: you do not configure the host,
you configure *through* a host that is permitted to talk to it.

```bash
ansible-playbook playbooks/rds.yml \
  -e rds_master_password="$(terraform -chdir=terraform/aws output -raw rds_password)"
```

The master password is generated by Terraform and never typed or committed —
which is also why the state bucket is encrypted.

## Say this in the interview

> "I ran both. RDS for anything where patching and backups are undifferentiated
> work — which is most things. Self-managed when I need superuser, an extension
> AWS doesn't support, or a very specific tuning.
>
> The two that catch people: you're not superuser on RDS, and restoring an
> automated backup gives you a whole new instance with a new endpoint, not a
> table back. So I still take logical dumps for granular recovery. And access
> control moves from `pg_hba.conf` to security groups — I scoped mine to the lab
> security group rather than a CIDR, so it survives instances being replaced."
