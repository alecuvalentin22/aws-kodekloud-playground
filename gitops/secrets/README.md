# Secrets in a public GitOps repository

The repo is public. A `Secret` in a public repo is a leaked credential — base64
is an encoding, not encryption, and `kubectl get secret -o yaml` output pasted
into git is the single most common GitOps mistake.

Both approaches here put **ciphertext** in git and do the decryption inside the
cluster. Neither requires a secret manager, and both are done here because they
fail in different places, which is the interesting part.

## The difference that matters

|  | Sealed Secrets | SOPS + age |
|---|---|---|
| encrypts | the whole `Secret`, into a `SealedSecret` CRD | the *values* inside an ordinary `Secret` |
| decrypted by | its own controller, at CRD reconcile time | **kustomize-controller**, during the build |
| works with Argo CD | **yes**, unmodified | no — needs a config-management plugin |
| works with Flux | yes | **yes**, natively (`spec.decryption`) |
| key lives | in-cluster, generated by the controller | wherever you put it — file, KMS, Vault |
| diffable in git | no, ciphertext is one opaque blob | **yes**, the structure stays readable |
| encrypting requires | the cluster (fetch its public cert) | nothing, just the recipient's public key |
| scoped to | one namespace **and** one name, by default | nothing — a decryptable file is decryptable |

Read the last two rows together, because they trade off directly.

**Sealed Secrets binds ciphertext to a namespace/name.** Move the `SealedSecret`
to another namespace and it stops decrypting — the namespace is part of the
encrypted envelope. That is a genuinely useful property in a multi-tenant repo:
a tenant cannot lift another tenant's ciphertext into their own directory and
have the controller decrypt it for them. SOPS has no equivalent; anyone holding
the age key decrypts anything encrypted to it.

**SOPS keeps the file readable.** A `SealedSecret` diff is noise — one giant
blob changes and a reviewer learns nothing. A SOPS diff shows *which key*
changed, with the value encrypted per-value. On a repo where secret changes get
reviewed, that is the deciding factor.

**Sealed Secrets needs the cluster to encrypt.** `kubeseal` fetches the
controller's public certificate from the live cluster, which means you cannot
prepare a secret for a cluster that does not exist yet, and rebuilding the
cluster invalidates every `SealedSecret` in the repo unless you backed the
sealing key up. That last sentence is the one that bites in a lab: **a
throwaway playground gets a new sealing key every time**, so committed
ciphertext is dead on the next rebuild.

```bash
# back the sealing key up, or accept that every SealedSecret in git is garbage
# after a cluster rebuild
kubectl -n kube-system get secret -l sealedsecrets.bitnami.com/sealed-secrets-key \
  -o yaml > sealing-key.yaml    # <- this file IS the master key. Never commit it.
```

SOPS has the mirror-image problem: the age private key has to reach the cluster
somehow, and that first secret cannot itself be encrypted with SOPS. Bootstrap
is a `kubectl create secret` by hand — the one imperative step neither tool
removes.

## What is committed here

- `sealed/` — a `SealedSecret`, safe in a public repo, decrypted by the
  sealed-secrets controller into a `Secret` named `demo-credentials`.
- `sops/` — the same secret encrypted with `age`, decrypted by Flux's
  kustomize-controller. The `.sops.yaml` at the repo root pins which keys get
  encrypted (`data` and `stringData` only — encrypting `metadata` would make
  the file unusable as a Kubernetes manifest).

Regenerate both with `../../scripts/secrets-seal.sh`.
